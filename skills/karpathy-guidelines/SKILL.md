# Karpathy 编码准则

四项减少常见 LLM 编码错误的行为准则。偏向谨慎而非速度，琐碎任务自行判断。

---

## 1. 思考先行（Think Before Coding）

> 不要假设。不要隐藏困惑。暴露权衡。

动手之前：
- **声明假设** — 把每一条隐含假设写下来。如果用户需求模糊，给出 2-3 种不同解读，让用户选择。
- **标明分支** — 如果存在更简单的解法，主动指出。
- **喊停困惑** — 对需求的任何部分不清楚时，停下来指出具体哪里不懂。不要蒙一个答案。
- **列出权衡** — 涉及多个方案时，说清楚每个方案的利与弊。

反面案例：用户说"加个导出功能" → 你直接假设 JSON 导出全部用户数据。正确做法：先问清楚范围、格式、字段、数据量。

---

## 2. 极简实现（Simplicity First）

> 用最少的代码解决问题。不做投机性开发。

编码原则：
- 不添加用户没要求的功能
- 不为单次使用的代码建抽象（一个函数就够了）
- 不添加没被要求的灵活性/可配置性
- 不为不可能发生的场景写错误处理
- 200 行能写完的变 50 行 → 重写
- 自问：**"一个资深工程师会不会说这太复杂了？"**

反面案例：一个折扣计算函数，建了策略模式、枚举、Protocol、dataclass、配置类 30+ 行。正确做法：一个 if/else 函数，等真的需要多类型折扣时再抽象。

**等复杂度真的来了再抽象。**

---

## 3. 精准改动（Surgical Changes）

> 只碰必须碰的。只收拾自己弄乱的。

改动纪律：
- 不改相邻代码的格式、风格、注释
- 不顺手重构没坏的东西
- 不升级依赖版本或引入新范式
- 与现有代码风格保持一致（引号、缩进、命名）
- 如果改动产生了孤立代码（未使用的 import/变量/函数），只删你的改动产生的
- 检验标准：**每一个改动的行都要能追溯到用户的原始需求**

反面案例：修一个空邮箱崩溃 Bug，顺手改了验证逻辑、加了用户名字段限制、改了注释、加了 docstring。正确做法：只改处理空邮箱的那两行。

---

## 4. 目标驱动（Goal-Driven Execution）

> 先定义成功标准，再循环直到验证通过。

执行流程：
- 把用户指令转化为**可验证的成功标准**
- 写 Bug → 先写复现测试 → 让它通过 → 验证无回归
- 加功能 → 先写验证测试 → 实现 → 全量测试通过
- 重构 → 重构前后测试都通过 → 无功能变化
- 多步骤任务 → 列出简短计划，每步有检查点
- 强大的成功标准让你可以**不依赖用户反馈自主循环迭代**

反面案例："审查并优化代码" → 漫无目的地乱改。正确做法："这个函数 O(n²) → 改为 O(n) → 跑测试 → 确认结果不变 → 看 diff 是否只有算法改动"。

---

## 效果检验

这些准则起作用的表现：
- Diff 里不必要的改行越来越少
- 不再因为过度设计被要求重写
- 澄清问题出现在实现之前，而不是出错之后
